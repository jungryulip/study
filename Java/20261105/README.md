# DAY 84 — Spring AI 대화 기억과 PDF RAG 파이프라인

> 2026-11-05 · Spring AI, H2, JPA, Embedding, PGVector, RAG, SSE, React

오늘은 Spring AI 챗봇이 이전 대화를 기억하도록 **H2와 JPA로 메시지를 저장**하고, PDF 문서를
잘게 나누어 임베딩한 뒤 **PGVector에서 관련 내용을 검색해 답변하는 RAG** 흐름을 실습했다.
백엔드에서는 문서 수집·청크 분할·벡터 저장·유사도 검색·스트리밍 응답을 연결했고,
프론트엔드에서는 PDF 업로드 진행 상태와 문서 기반 질의응답 화면을 구성했다.

## 오늘의 학습 흐름

```text
H2와 JPA로 대화 내역 저장
  ↓
이전 대화를 Prompt 메시지로 복원
  ↓
토큰·청크·문서와 임베딩 개념
  ↓
PDF 텍스트 추출과 청크 분할
  ↓
임베딩 생성 후 PGVector에 저장
  ↓
질문과 비슷한 청크 검색
  ↓
검색 문맥을 포함한 RAG 답변을 스트리밍
```

## 1. H2와 JPA로 챗봇 대화 저장하기

H2는 Java 환경에서 가볍게 사용할 수 있는 관계형 데이터베이스다. 별도 서버 없이 메모리
모드로 실행할 수 있어 기능을 빠르게 실습하고 확인하기 좋다. 이번에는 사용자의 질문과 AI의
답변을 하나의 메시지 엔티티로 저장했다.

| 항목 | 역할 |
| --- | --- |
| `ChatMessage` Entity | 메시지 ID, 사용자 구분값, 내용, 발신 주체, 생성 시각 저장 |
| `ChatMessageRepository` | 사용자별 메시지를 생성 시각 순서로 조회 |
| `CustomerSupportService` | 이전 대화를 불러와 Prompt를 만들고 새 대화를 저장 |
| 요청·응답 DTO | API 계층에서 필요한 데이터만 전달 |

### Entity와 DTO의 차이

- **Entity**는 데이터베이스 테이블과 연결되어 영속성 상태를 표현한다.
- **DTO**는 계층 사이 또는 API 요청·응답에서 필요한 값만 운반한다.
- Entity를 그대로 외부에 노출하지 않으면 테이블 구조와 API 계약을 분리할 수 있다.

```java
public interface ChatMessageRepository
        extends JpaRepository<ChatMessage, Long> {

    List<ChatMessage> findByUserIdOrderByCreatedAtAsc(String userId);
}
```

서비스는 저장된 메시지를 사용자 메시지와 AI 메시지로 다시 변환해 현재 질문 앞에 붙인다.
모델 호출이 끝나면 현재 질문과 답변을 함께 저장하므로 다음 요청에서도 대화 흐름을 이어갈 수
있다.

```text
사용자 ID로 과거 메시지 조회
  → 발신 주체에 따라 UserMessage·AssistantMessage로 변환
  → 시스템 지침 + 과거 대화 + 현재 질문으로 Prompt 구성
  → AI 응답 생성
  → 현재 질문과 답변 저장
```

메모리 DB는 애플리케이션을 다시 시작하면 데이터가 사라질 수 있다. 학습용 확인에는 편하지만,
운영 환경에서는 영구 저장소와 사용자 인증을 함께 설계해야 한다.

## 2. RAG와 임베딩

RAG(Retrieval-Augmented Generation)는 모델이 가진 일반 지식만으로 답하지 않고, 먼저 저장된
문서에서 질문과 관련된 내용을 검색한 뒤 그 결과를 근거로 답변을 생성하는 방식이다.

```text
Retrieval: 질문과 관련된 문서 조각 검색
  +
Generation: 검색된 문맥을 바탕으로 답변 생성
```

임베딩은 문장이나 문서를 의미를 담은 숫자 벡터로 바꾸는 과정이다. 의미가 비슷한 텍스트는
벡터 공간에서도 가까운 위치에 놓이는 성질을 이용해 관련 문서를 찾는다.

| 개념 | 정리 |
| --- | --- |
| Token | 모델이 텍스트를 처리하는 작은 단위 |
| Chunk | 검색과 입력에 알맞도록 문서를 나눈 조각 |
| Embedding | 텍스트의 의미를 수치 벡터로 표현한 값 |
| Similarity Search | 질문 벡터와 가까운 문서 벡터를 찾는 검색 |
| Top-K | 유사도가 높은 결과 중 몇 개를 사용할지 정하는 값 |
| Threshold | 관련성이 낮은 결과를 제외하는 최소 기준 |
| Metadata | 출처·페이지·문서 종류 등을 함께 저장하는 부가 정보 |

문서를 너무 크게 나누면 필요한 부분을 정확히 찾기 어렵고, 너무 작게 나누면 앞뒤 맥락이
끊길 수 있다. 청크 크기와 겹침 범위는 문서 성격과 질문 방식에 맞춰 검증해야 한다.

## 3. PDF를 PGVector에 저장하는 흐름

PDF 업로드 API는 파일을 임시 저장한 뒤 페이지별 텍스트를 읽고, 토큰 기준 청크로 분할해
임베딩 벡터를 만든다. 생성된 벡터와 원문 청크는 PostgreSQL의 `pgvector` 확장에 저장했다.

```text
PDF 업로드
  → PagePdfDocumentReader로 페이지별 텍스트 추출
  → TokenTextSplitter로 청크 분할
  → 임베딩 모델로 벡터 생성
  → PGVector VectorStore에 청크·벡터·메타데이터 저장
```

```java
List<Document> pages = pdfReader.get();
List<Document> chunks = tokenTextSplitter.apply(pages);
vectorStore.accept(chunks);
```

업로드한 파일은 처리 후 삭제하도록 `finally`에서 정리해야 한다. 파일 형식과 크기 제한,
악성 파일 검사, 저장 위치 분리도 실제 서비스에서 추가로 고려할 항목이다.

## 4. 문서 기반 질문과 답변

질문이 들어오면 같은 임베딩 모델로 질문 벡터를 만들고, VectorStore에서 가장 가까운 청크를
검색한다. 이번 실습에서는 유사도가 높은 청크 두 개를 가져와 문맥으로 묶고, 질문과 함께
프롬프트에 넣었다.

```java
List<Document> documents = vectorStore.similaritySearch(
    SearchRequest.builder()
        .query(question)
        .topK(2)
        .build()
);
```

프롬프트에는 **제공된 문맥 안에서만 답하고, 근거를 찾지 못하면 찾을 수 없다고 알리도록**
규칙을 넣었다. 이 방식은 모델의 임의 추측을 줄이는 데 도움이 되지만, 검색 결과 자체가
부정확할 수 있으므로 출처 표시와 검색 품질 평가가 필요하다.

```text
질문
  → 질문 임베딩
  → PGVector 유사도 검색
  → 검색 청크를 Context로 구성
  → Context + Question으로 모델 호출
  → 문서 기반 답변
```

실습에서는 문서에 없는 질문에 “관련 정보를 찾을 수 없습니다”라고 응답하는지 확인해,
모델이 검색 범위를 벗어나 임의로 답하지 않도록 하는 기본 동작도 검증했다.

## 5. 스트리밍 응답과 React 화면

백엔드는 `text/event-stream` 형식으로 모델 응답을 조금씩 전달하고, 프론트엔드는 도착하는
텍스트를 현재 AI 메시지에 이어 붙였다. 긴 답변도 모두 생성될 때까지 기다리지 않고 바로 읽기
시작할 수 있다.

React 화면에서는 다음 흐름을 구현했다.

- PDF 파일만 선택하고 최대 20MB인지 확인하는 업로드 검증
- 업로드 진행률과 텍스트 추출·청크 분할·임베딩·저장 단계 표시
- 업로드 이력과 성공·실패 상태 관리
- 사용자 질문과 AI 답변을 메시지 목록으로 관리
- 스트림 수신 중 답변을 실시간으로 갱신
- 관련 문서를 찾지 못한 경우의 안내와 오류 상태 처리

## 6. JPA와 MyBatis 비교

| 항목 | JPA | MyBatis |
| --- | --- | --- |
| 중심 | 객체와 엔티티 관계 | SQL과 조회 결과 매핑 |
| 기본 CRUD | Repository로 반복 코드 감소 | SQL을 직접 작성해 명확하게 제어 |
| 복잡한 조회 | JPQL·Query Method 등 사용 | 복잡한 SQL을 세밀하게 작성하기 편리 |
| 주의점 | 영속성 컨텍스트와 연관관계 이해 필요 | SQL 중복과 매핑 코드를 관리해야 함 |

이번 대화 저장 실습에서는 간단한 엔티티 CRUD와 정렬 조회가 중심이어서 Spring Data JPA를
사용했다. 기술은 선호보다 데이터 구조, 쿼리 복잡도와 팀의 유지보수 방식을 기준으로 선택해야
한다.

## 7. 보안과 공개 원칙

AI 키와 데이터베이스 접속정보는 코드에 직접 적지 않고 환경변수로 주입한다.

```properties
spring.ai.openai.api-key=${OPENAI_API_KEY}
spring.datasource.url=${DB_URL}
spring.datasource.username=${DB_USERNAME}
spring.datasource.password=${DB_PASSWORD}
```

이번 공개 기록에는 다음 자료를 포함하지 않았다.

- 원본 PDF와 수업 자료 이미지
- 실제 또는 로컬 테스트용 데이터베이스 접속정보가 있는 설정·백업 파일
- API 요청 기록과 사용자 식별값이 보이는 Postman 화면
- H2 세션 ID와 사용자 데이터가 보이는 콘솔 화면
- 원본 프로젝트, `node_modules`, `build`, `bin`, `.gradle`, JAR·CLASS 파일
- API 키가 포함될 수 있는 로그와 빌드 산출물

공개 전에 확인한 자료에서는 실제 OpenAI API 키나 토큰은 발견되지 않았다. 다만 로컬 개발용
데이터베이스 접속정보도 저장소에는 올리지 않고 환경변수로 분리하는 습관이 필요하다.

## 오늘의 정리

- H2와 JPA를 이용하면 사용자별 대화를 저장하고 다음 Prompt에서 다시 활용할 수 있다.
- RAG는 문서를 검색한 결과를 LLM의 문맥으로 제공해 답변의 근거 범위를 좁힌다.
- PDF는 텍스트 추출·청크 분할·임베딩을 거쳐 PGVector에 저장할 수 있다.
- 질문도 임베딩한 뒤 Top-K 유사도 검색으로 관련 청크를 선택한다.
- SSE 스트리밍을 이용하면 React 화면에 AI 답변을 실시간으로 표시할 수 있다.
- 키·접속정보·원문 자료·세션 정보·빌드 산출물은 공개 기록에서 제외해야 한다.
