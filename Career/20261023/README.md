# DAY 73 — 기술 선택의 근거와 Java·Spring 웹 동작 원리

> 2026-10-23 · Problem Solving, Web Architecture, Java, Spring, Database

어제 신입 개발자가 준비할 전체 기술 지도를 확인했다면, 오늘은 각 기술이 실제 웹 서비스에서
어떤 역할을 하는지 연결해서 살펴봤다. 프로젝트에서는 기술 이름을 많이 나열하는 것보다
**어떤 문제를 해결하기 위해 왜 선택했고, 어떻게 검증했는지** 설명하는 능력이 중요하다는 점을
중심으로 정리했다.

## 1. 기술 선택은 문제와 측정에서 시작한다

“Redis를 사용했다”는 사실만으로는 기술 선택의 타당성을 보여주기 어렵다. 다음과 같이 문제부터
결과까지 이어지는 흐름을 설명할 수 있어야 한다.

```text
문제 발견
  ↓
원인에 대한 가설
  ↓
문제 재현과 현재 상태 측정
  ↓
해결 방법 비교·선택
  ↓
적용 후 다시 측정
  ↓
결과와 남은 문제 기록
```

예를 들어 같은 데이터를 반복 조회해 DB I/O(데이터 입출력)와 응답 시간이 늘어난 상황이라면 캐싱을 검토할 수
있다. 여러 서버가 캐시를 공유해야 한다면 메모리 기반 저장소인 Redis가 선택지가 될 수 있다.
하지만 Redis를 추가한다고 항상 빨라지는 것은 아니다.

- 어떤 데이터를 얼마 동안 저장할지 정해야 한다.
- 원본 데이터가 바뀔 때 캐시를 갱신하거나 제거하는 전략이 필요하다.
- 잠시 오래된 데이터가 제공되어도 괜찮은지 판단해야 한다.
- 적용 전후의 응답 시간과 DB 조회 횟수를 같은 조건에서 비교해야 한다.

포트폴리오에는 실제 측정값과 테스트 방법을 남기고, 측정하지 않은 수치를 만들어 쓰지 않는다.

## 2. 내가 이해하는 문제에서 프로젝트를 시작한다

**도메인 지식**은 특정 분야의 업무와 규칙에 관한 지식이다. 일상에서 겪은 불편이나 잘 아는
분야를 프로젝트 주제로 선택하면 사용자, 업무 흐름과 예외 상황을 더 구체적으로 정의할 수 있다.

예를 들어 팝업 매장 운영 경험이 있다면 입장 대기와 혼잡이 발생하는 시점, 직원에게 필요한 정보,
방문객 안내와 현장 예외를 기능 요구사항으로 발전시킬 수 있다. 반면 비상탈출 경로처럼 안전과
책임이 중요한 서비스는 기술적으로 구현할 수 있는지뿐 아니라 현장 조건, 안전 기준, 책임 범위와 실제 적용
가능성을 별도로 검토해야 한다.

Spotify 같은 외부 API를 활용할 때도 제공 기능만 보지 않고 이용 약관, 호출 제한, 인증 방식과
데이터 사용 조건을 함께 확인해야 한다.

## 3. 브라우저부터 DB까지의 웹 요청 흐름

```text
브라우저
   ↓ 요청
웹 서버 — Apache·Nginx
   ├─ 정적 자원 요청 → 파일 전달
   └─ 프로그램 처리가 필요한 요청
               ↓
       WAS — Tomcat·WebSphere
               ↓ 필요한 경우
              DB
```

| 구성 요소 | 역할 |
| --- | --- |
| 브라우저 | 화면을 표시하고 사용자의 요청을 전송 |
| 웹 서버 | 정적 파일을 제공하고 필요한 요청을 애플리케이션으로 전달 |
| WAS | 서버 프로그램을 실행해 동적인 응답을 생성 |
| DB | 회원·상품·주문 같은 데이터를 저장하고 조회 |

Apache와 Nginx는 대표적인 웹 서버다. Tomcat은 엄밀히 말하면 자바 Servlet을 실행하는 컨테이너이고,
WebSphere는 더 넓은 기업용 Java 기능을 제공하는 애플리케이션 서버다.

이 구분은 역할을 이해하기 위한 기본 구조이며 항상 서버를 각각 따로 설치해야 한다는 의미는
아니다. Tomcat도 정적 파일을 제공할 수 있고, DB 없이 계산만 수행해 응답하는 프로그램도 가능하다.

### 정적 자원과 동적 처리

- **정적 자원**: 저장된 HTML·CSS·JavaScript·이미지 파일을 그대로 전달한다.
- **동적 처리**: 로그인 확인, 주문 조회나 결제 금액 계산처럼 요청에 따라 프로그램이 응답을 만든다.

JavaScript가 브라우저에서 화면을 동적으로 바꾸더라도 서버가 저장된 JavaScript 파일을 그대로
전달했다면 그 파일 자체는 정적 자원이다.

## 4. Bootstrap과 Spring Boot, 파일 위치

| 구분 | 역할 |
| --- | --- |
| Bootstrap | 버튼·메뉴·입력창 등 화면을 구성하는 CSS·JavaScript 도구 모음 |
| Spring Boot | Spring 기반 서버 애플리케이션의 설정과 실행을 간소화하는 도구 |

Bootstrap 파일은 브라우저가 받는 정적 자원이고, Spring Boot는 서버 쪽 애플리케이션을 구성한다.
Spring Boot는 내장 Tomcat을 사용하는 구성이 흔해 별도 Tomcat 설치 없이 실행할 수 있다.

수업의 프로젝트 기준은 Spring Boot 3.x와 Java 17이다. Spring Boot 3부터 Servlet 등 Jakarta EE
관련 API의 패키지가 기존 `javax.*`에서 `jakarta.*`로 바뀌었으므로 오래된 예제와 섞어 쓸 때
주의한다. 모든 Java의 `javax` 패키지가 바뀌었다는 뜻은 아니다.

### 전통적인 WAR 프로젝트

```text
src/main/webapp/
├── css/
├── js/
├── images/
└── WEB-INF/
    └── views/
        └── home.jsp
```

`WEB-INF` 아래의 파일은 브라우저가 주소로 직접 요청할 수 없고 서버 내부에서 연결해야 한다.
따라서 직접 접근을 막을 JSP 화면을 둘 수 있지만, 브라우저가 직접 요청해야 하는 CSS·JavaScript와
이미지까지 모두 넣으면 안 된다.

### 일반적인 Spring Boot 프로젝트

```text
src/main/resources/
├── static/       # CSS, JavaScript, 이미지
└── templates/    # Thymeleaf 같은 서버 템플릿
```

정답인 폴더 구조가 하나로 고정된 것은 아니며 화면 기술과 배포 방식에 맞춰 선택한다.

## 5. 보일러플레이트와 어노테이션

**보일러플레이트**는 getter, setter, 생성자와 `toString()`처럼 비슷한 형태로 반복 작성하는 코드다.
Lombok은 어노테이션을 읽어 컴파일 과정에서 이런 코드를 만들어 준다.

```java
@Getter
@Setter
class Member {
    private String name;
}
```

어노테이션 자체가 기능을 실행하는 것은 아니다. 표시를 읽고 처리하는 도구나 프레임워크가 따로
있다.

- Lombok의 `@Getter`·`@Setter`: 주로 컴파일 과정에서 코드 생성
- Spring의 `@Service`: 실행 중 Spring이 객체를 찾아 관리할 때 사용
- Spring의 `@Transactional`: 프록시 등을 통해 트랜잭션 동작을 적용할 때 사용

## 6. ORM·MyBatis와 트랜잭션

### 데이터 접근 방식

| 구분 | 중심 개념 |
| --- | --- |
| ORM | 객체와 관계형 DB 테이블 사이의 차이를 매핑 |
| MyBatis | 개발자가 작성한 SQL과 Java 객체를 연결 |

JPA는 Java의 대표적인 ORM 표준이고 Hibernate는 대표적인 구현체다. MyBatis는 ORM이 아니라 SQL
매퍼이며 SQL을 XML뿐 아니라 어노테이션 등으로도 작성할 수 있다. 프로젝트가 요구하는 쿼리 제어,
생산성과 유지보수 방식을 비교해 선택한다.

### 트랜잭션

트랜잭션은 여러 작업을 하나의 처리 단위로 묶는다. 계좌이체라면 출금과 입금이 함께 성공해야 하며,
중간에 실패하면 이전 변경도 취소해야 데이터가 어긋나지 않는다.

```java
@Transactional
public void transfer() {
    // A 계좌에서 출금
    // B 계좌에 입금
}
```

하나의 업무가 여러 DB 작업을 묶는 경우가 많아 `@Transactional`은 서비스 계층에서 자주 사용되지만,
반드시 서비스에만 사용할 수 있는 것은 아니다. 기본 설정에서는 런타임 예외와 `Error`가 롤백
대상이며 체크 예외는 별도 설정이 필요할 수 있다.

## 7. 클래스·객체와 JVM 메모리

```java
class Phone {
    String name;
    String number;
    static int totalCount;
}

Phone first = new Phone();
Phone second = new Phone();
```

- **클래스**: 객체의 설계도이자 새로운 데이터 타입
- **스택**: 메서드 호출마다 스택 프레임이 생기며 지역변수와 실행 중인 값을 관리
- **힙**: `new`로 만든 객체와 배열이 생성되는 공간
- **참조변수**: 객체 전체가 아니라 객체를 가리키는 참조값을 보관
- **static 필드**: 객체별 값이 아니라 같은 클래스가 공유하는 값

참조값을 주소처럼 이해할 수는 있지만 Java에서 직접 다루는 물리적 메모리 주소라고 단정하지
않는다. 객체나 클래스의 크기도 항상 4바이트처럼 고정되지 않으며 JVM 환경과 객체의 필드에 따라
달라진다.

메서드 실행이 끝나면 스택 프레임은 제거되지만 힙의 객체가 즉시 삭제되는 것은 아니다. 더 이상
애플리케이션에서 도달할 수 없는 객체가 GC의 수거 대상이 된다. `static` 값도 프로그램이 종료된 뒤까지
영구적으로 남는 것은 아니다.

### main·static과 생성자

`main`은 전역함수가 아니라 클래스에 속한 static 메서드다. 객체를 만들지 않고 시작점으로 호출할
수 있으며, 모든 클래스가 `main`을 가질 필요는 없다.

생성자는 객체가 만들어질 때 초기 상태를 설정한다. 클래스 이름과 같고 반환 타입을 작성하지 않는다.
필수 값을 매개변수로 받게 만들 수 있지만 빈 문자열처럼 값의 유효성까지 보장하려면 생성자 안에서
별도로 검사해야 한다.

## 8. IoC·DI·Bean

```java
@Service
class OrderService {
    private final PaymentService paymentService;

    OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}
```

- **IoC**: 객체 생성과 연결 등의 제어를 프레임워크에 맡기는 개념
- **DI**: 필요한 객체를 외부에서 전달받는 방식이자 IoC를 구현하는 방법 중 하나
- **Bean**: Spring 컨테이너가 생성하고 관리하는 객체
- **Spring 컨테이너**: Bean의 생성·연결·생명주기를 관리하는 공간

DI를 적용해도 객체는 여전히 힙에 생성된다. 달라지는 것은 메모리 영역이 아니라 **누가 객체를
생성하고 연결하며 관리하는가**이다.

## 9. 동기화와 직렬화

### Vector와 ArrayList

동기화는 여러 스레드가 공유 데이터를 사용할 때 작업이 꼬이지 않도록 접근을 조절하는 것이다.
`Vector`는 개별 메서드에 동기화를 적용하지만, 여러 메서드 호출을 합친 작업 전체까지 원자적으로
보장하지는 않는다.

```java
if (!vector.isEmpty()) {
    vector.remove(0);
}
```

`isEmpty()`와 `remove()`가 각각 안전해도 두 호출 사이에 다른 스레드가 데이터를 바꿀 수 있다.
`ArrayList`는 자체적인 스레드 안전을 보장하지 않으므로 공유 변경이 있다면 별도 동기화나 동시성
컬렉션을 검토해야 한다.

### 직렬화

직렬화는 객체의 상태를 JSON이나 바이트처럼 저장·전송 가능한 형태로 바꾸는 과정이고, 역직렬화는
그 표현을 다시 객체로 만드는 과정이다. 직렬화한 데이터는 파일에 저장하거나 네트워크로 전송할 수
있지만, 직렬화 자체가 통신을 수행하는 것은 아니다.

## 10. 주문 요청으로 전체 흐름 연결하기

```text
Bootstrap으로 구성한 화면에서 주문 버튼 클릭
  ↓
브라우저가 주문 요청 전송
  ↓
웹 서버가 페이지의 정적 자원을 제공하고 주문 요청을 WAS로 전달
  ↓
Spring 컨테이너가 관리하는 Bean이 DI로 연결되어 업무 처리
  ↓
Service의 트랜잭션 안에서 여러 DB 작업 수행
  ↓
MyBatis 또는 ORM으로 DB 접근
  ↓
처리 결과를 JSON 등으로 직렬화해 응답
```

요청을 처리하는 동안 객체와 배열은 힙에 생성되고 메서드 호출마다 스택 프레임이 생긴다. 여러
요청이 같은 데이터를 수정한다면 트랜잭션뿐 아니라 동시 접근 문제도 함께 검토해야 한다.

## 오늘의 정리

오늘은 웹 서버, Spring, DB와 JVM 개념을 따로 외우는 대신 하나의 요청이 처리되는 흐름 안에서
연결해 봤다. 기술을 선택할 때는 이름이나 유행보다 해결할 문제, 선택 이유, 측정 가능한 결과와
남은 한계를 기록해야 한다.

앞으로 프로젝트를 정리할 때는 **문제 → 가설 → 측정 → 선택 → 검증 → 개선점**의 순서로 설명하고,
각 기술이 전체 구조에서 담당하는 역할을 내 코드와 함께 설명할 수 있도록 준비해야겠다.
