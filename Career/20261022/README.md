## 2. SPA와 MPA

### SPA — Single Page Application

SPA는 처음 받은 HTML 문서를 바탕으로 브라우저가 화면을 동적으로 갱신하는 방식이다. React나
Vue가 대표적인 선택지이며, 서버로부터 주로 JSON 데이터를 받아 `fetch`나 `axios` 같은 비동기
통신으로 화면에 반영한다.

- 화면 전체를 다시 불러오지 않아 자연스러운 사용자 경험을 만들기 좋다.
- 프론트엔드와 백엔드의 역할을 API를 기준으로 나누기 좋다.
- 라우팅, 상태 관리, 인증과 오류 처리 등 브라우저에서 고려할 부분이 많다.
- 초기 로딩, 접근성과 검색 엔진 최적화를 별도로 고려해야 할 수 있다.

### MPA — Multi Page Application

MPA는 페이지를 이동할 때 서버가 새로운 HTML 문서를 만들어 전달하는 방식이다. Spring MVC와
Thymeleaf 같은 서버 템플릿 엔진을 함께 사용하는 구성이 한 예다.

- 서버에서 데이터와 화면을 함께 구성하기 쉽다.
- 페이지별 구조와 URL이 명확하다.
- 페이지 이동 시 전체 문서를 다시 요청하는 경우가 많다.

“SPA는 프론트가 바쁘고 MPA는 백엔드가 바쁘다”는 말은 입문 단계의 비유로 이해했다. 실제
업무량은 인증, 상태 관리, 캐싱, API와 배포 구조에 따라 달라진다. React라고 항상 SPA인 것도,
Thymeleaf라고 모든 화면이 전통적인 MPA인 것도 아니므로 **렌더링 책임을 어디에 두는가**를
기준으로 설명하는 편이 정확하다.

## 3. 오버로딩과 오버라이딩

| 구분 | 오버로딩(Overloading) | 오버라이딩(Overriding) |
| --- | --- | --- |
| 의미 | 같은 이름의 메서드를 매개변수 구성에 따라 여러 개 정의 | 상위 클래스의 메서드를 하위 클래스가 재정의하거나 구현 클래스가 인터페이스 메서드를 구현 |
| 조건 | 매개변수의 개수·타입·순서 중 하나 이상이 달라야 함 | 메서드 이름과 매개변수 구성이 같아야 함 |
| 상속 관계 | 필요하지 않음 | 상속 또는 인터페이스 구현 관계가 필요함 |
| 결정 시점 | 주로 컴파일 시점 | 실행 시점의 실제 객체에 따라 결정 |

```java
class Calculator {
    int add(int left, int right) { return left + right; }
    double add(double left, double right) { return left + right; } // 오버로딩
}

class Animal {
    void sound() { System.out.println("동물 소리"); }
}

class Dog extends Animal {
    @Override
    void sound() { System.out.println("멍멍"); } // 오버라이딩
}
```

반환 타입만 바꾸는 것은 오버로딩이 아니다. 오버라이딩할 때 `@Override`를 사용하면 잘못된
재정의를 컴파일 단계에서 확인할 수 있다.

## 4. 신입 개발자의 취업 준비

이력서와 자기소개서 같은 서류가 먼저 검토되므로 읽는 사람이 기술과 경험을 빠르게 이해할 수
있게 작성해야 한다. 정보처리기사, SQLD, 어학 점수와 학점도 도움이 될 수 있지만 회사마다 기준이
다르고, 자격증만으로 개발 역량을 증명할 수는 없다.

모든 기술을 같은 깊이로 배우기보다 한 가지 주력 기술을 깊게 다루고, 연관 기술은 협업하고
문제를 해결할 수 있는 수준까지 이해하는 **T자형 역량**을 목표로 한다. 신입이라도 SQL의 기본
CRUD와 JOIN, 데이터 흐름을 이해하고 직접 결과를 검증할 수 있어야 한다.

### 포트폴리오에서 보여줄 것

- 내가 맡은 역할과 실제 구현 범위
- 기능을 만든 이유와 기술을 선택한 근거
- 발생한 문제, 원인 분석과 해결 과정
- 테스트 방법과 검증 결과
- Pull Request, 코드 리뷰와 충돌 해결 등 협업 기록
- 구현 후 발견한 한계와 다음 개선 방향

AI가 제안한 코드를 그대로 복사하는 데 그치지 않고, 실행 결과와 예외 상황을 직접 테스트해야
한다. 포트폴리오에도 AI를 어디에 활용했고 어떤 기준으로 검증·수정했는지를 남기면 문제 해결
과정을 더 분명하게 보여줄 수 있다.

## 5. 프론트엔드 로드맵

React 문법만 외우기보다 그 기반이 되는 JavaScript와 브라우저의 동작을 먼저 이해해야 한다.

## 6. 백엔드 로드맵

### Java와 설계 기초

- 클래스·객체, 상속·포함·다형성과 인터페이스
- 제네릭과 `List`, `Set`, `Map` 등 컬렉션 프레임워크
- 예외 처리, 입출력, 람다식과 Stream
- UML 클래스 다이어그램의 상속·연관·포함 관계 읽기

### Spring과 MVC

- Spring Legacy: 기존 시스템을 이해하고 유지보수할 때 필요한 구조
- Spring Boot: 설정을 간소화해 애플리케이션을 빠르게 구성
- DI(Dependency Injection): 필요한 의존성을 외부에서 주입
- AOP: 로깅·트랜잭션·보안처럼 반복되는 관심사를 핵심 로직과 분리
- MVC: 요청 처리, 비즈니스 로직, 데이터와 화면의 책임을 분리

| 계층 | 주요 책임 |
| --- | --- |
| Controller | 요청을 받고 적절한 처리 흐름을 선택 |
| Service | 핵심 비즈니스 규칙과 작업 순서를 처리 |
| DAO·Repository | 데이터 조회·저장·수정·삭제 |
| DTO·Domain | 계층 간 데이터 전달과 도메인 표현 |
| View | SPA 또는 MPA 방식으로 결과를 사용자에게 표현 |

MyBatis는 SQL을 직접 작성하며 세밀하게 제어하는 방식이고, JPA는 객체와 관계형 데이터베이스를
매핑하는 방식이다. 어느 하나를 단순히 부가 기술로 보기보다 프로젝트 요구사항과 팀의 상황에
따라 선택한다.

MSA는 서비스를 작은 단위로 나누어 독립적으로 개발·배포하는 아키텍처다. MVC에 기능 하나를
더하는 개념은 아니며 운영 복잡도가 커질 수 있으므로, 먼저 단일 애플리케이션의 계층 구조와
배포 흐름을 이해한 뒤 필요성을 판단해야 한다.

## 7. 데이터베이스 로드맵

### SQL과 모델링

- JOIN, 서브쿼리, 집계, 트랜잭션
- 인덱스의 목적과 조회·변경 성능의 트레이드오프
- 요구사항을 바탕으로 한 개념적·논리적·물리적 설계
- 1NF·2NF·3NF 정규화와 조회 성능을 위한 반정규화
- 기본키·외래키·제약조건을 통한 데이터 무결성

### PL/SQL

PL/SQL은 변수, 조건문과 반복문 같은 프로그램 요소를 SQL에 결합한 Oracle의 절차형 언어다.
프로시저, 함수, 커서와 트리거를 이용해 데이터베이스 가까이에서 작업을 처리할 수 있다. 사용
자체가 프로젝트의 수준을 높여 주는 것은 아니므로 성능, 유지보수성과 이식성을 함께 고려해야 한다.
