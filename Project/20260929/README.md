# DAY 54 — 미니프로젝트 II 디자인 시스템과 기획 발표 완성

> 2026-09-29 · CertMaster, 디자인 시스템, 다크·라이트 모드, 컴포넌트 라이브러리, 기획 발표

오늘은 미니프로젝트 II에서 설계 중인 자격증 학습 웹사이트 **CertMaster**의 디자인 시스템을
정리하고, 서비스의 목적과 사용자 흐름을 설명하는 기획 발표 자료를 완성했다. 전날 만든 UI
목업을 개별 화면으로만 두지 않고 색상·글꼴·간격과 컴포넌트 규칙으로 확장했으며, 발표 자료에는
문제 정의부터 데이터 흐름, 구현 순서와 위험 대응까지 하나의 이야기로 연결했다.

## 1. 오늘의 목표

- 화면마다 반복해서 사용할 디자인 토큰과 UI 규칙 정의하기
- 다크·라이트 모드에서 같은 의미와 위계를 유지하도록 색상 체계 만들기
- 버튼, 입력창, 배지, 카드와 내비게이션의 변형과 상태 정리하기
- 문제 풀이부터 복습·취약점 분석·AI 보완 학습까지의 서비스 흐름 설명하기
- 정보 구조, 데이터 모델, 권한, 시스템 구성과 MVP 범위를 발표 자료로 완성하기

## 2. 디자인 시스템의 기초

### 의미 중심 색상 토큰

색상 이름을 화면별로 직접 지정하기보다 역할에 따라 토큰을 나누었다. 배경은 기본·표면·강조·호버·
선택 상태로, 테두리는 기본·강조·포커스로, 텍스트는 주·보조·약한 텍스트와 반전 텍스트로 구분했다.
브랜드 색상과 성공·경고·오류·정보 상태도 별도 토큰으로 정의해 다크 모드와 라이트 모드에서 같은
의미를 유지하도록 했다.

### 글꼴과 간격

제목, 페이지 제목, 섹션 제목, 카드 제목, 본문, 보조 설명, 메타데이터와 버튼 텍스트의 크기와 굵기를
정리했다. 여백은 8px 단위의 규칙을 기준으로 맞추고, 작은 요소부터 큰 카드까지 사용할 모서리
반경과 기본·강조·포커스 테두리를 나누었다. 그림자는 어두운 화면에서는 최소화하고 밝은 화면에서만
약하게 사용해 정보 계층이 흐려지지 않도록 했다.

```text
의미 토큰 → 다크·라이트 모드 매핑 → 공통 컴포넌트 → 실제 화면 패턴
```

## 3. 컴포넌트와 화면 패턴

버튼은 `Primary`, `Secondary`, `Ghost`, `Danger` 용도와 크기별 규칙을 정하고 기본·호버·비활성화
상태를 비교했다. 입력창, 배지, 알림, 카드와 내비게이션도 다크·라이트 모드에서 같은 구조를 유지하도록
정리했다.

컴포넌트가 실제 화면에서 어떻게 조합되는지도 함께 확인했다.

- 자격증 진행률과 다음 행동을 보여 주는 학습 폴더 카드
- 회차, 문제 수와 진행 상태를 비교하는 시험 세트 테이블
- 학습 맥락을 유지하며 질문할 수 있는 AI 채팅 패턴
- 진행률, 풀이 수, 복습 대상과 최근 기록을 모은 `내 학습` 화면

## 4. 기획 발표의 사용자 흐름

서비스의 출발점은 학습 도구가 여러 곳에 흩어져 있고, 정답을 맞혔다는 사실만으로는 이해 여부를
판단하기 어렵다는 문제였다. 이를 해결하기 위해 다음 흐름을 발표 자료에 담았다.

```text
학습 홈 → 회차 선택 → 문제 풀이 → 제출·채점 → 오답·복습 표시
        → 취약 키워드 분석 → AI 요약·질문 → 다시 학습
```

전체 정보 구조는 `HOME`, `STUDY`, `MY STUDY`, `INSIGHT`, `ADMIN`으로 구분했다. 사용자가
공부를 시작하고 기록을 확인하는 경로와 관리자가 콘텐츠를 운영하는 경로가 섞이지 않도록 역할을
나누었다.

## 5. 복습 규칙과 AI의 역할

복습 대상은 오답 문제와 사용자가 직접 복습 표시한 문제의 합집합으로 구성해 중복을 방지한다.
`잘 모르겠어요`는 정오답과 다른 학습 상태로 저장해, 우연히 맞힌 문제도 다시 확인할 수 있도록
설계했다.

취약 키워드와 점수는 서버의 정해진 규칙으로 계산하고, AI는 그 결과를 바탕으로 설명·요약·추가
질문을 돕는 역할만 맡긴다. AI가 정답이나 취약도를 직접 결정하지 않게 해 학습 결과의 기준이
흔들리지 않도록 했다.

## 6. 데이터·권한·시스템 설계

회원, 자격증, 과목, 시험 세트, 문제, 응시 기록, 키워드, 취약점과 AI 학습 기록을 중심으로 데이터
관계를 정리했다. 권한은 비회원·일반 사용자·관리자로 나누고, 로그인 사용자의 정보는 요청 값보다
서버 세션을 기준으로 확인하도록 설계했다.

기술 역할은 다음과 같이 구분했다.

- React: 화면, 상태와 사용자 상호작용
- Spring Boot·Java: 인증, 채점, 취약도 계산과 업무 규칙
- Oracle·SQL: 회원, 문제, 응시와 학습 기록 저장
- 외부 AI API: 서버가 전달한 학습 맥락을 설명하고 질문에 응답

## 7. MVP 순서와 위험 대응

MVP는 `문제 조회 → 응시·채점 → 취약 분석 → AI 학습` 순서로 범위를 나누었다. 핵심 학습 흐름을
먼저 검증한 다음 AI 기능을 붙이면 일정과 오류 위험을 줄일 수 있기 때문이다. 콘텐츠 권리, AI의
부정확한 답변, 개인정보, 기능 범위 증가와 외부 API 장애·비용은 별도 위험으로 정리하고 각각의
대응 방향을 발표 자료에 포함했다.

## 9. 공개 전 정리

원본 PPTX와 Figma 편집 화면 캡처에는 팀원 이름과 계정 프로필이 포함되어 있어 저장소에 올리지
않았다. 공개용 발표 자료는 표지의 이름을 원본 이미지에서 제거하고 문서 메타데이터도 다시 작성했다.
발표 자료와 테이블 구성이 다른 별도 ERD 원문은 버전을 통일한 뒤 공개하기 위해 이번 업로드에서
제외했다. `.DS_Store` 같은 운영체제 파일도 포함하지 않았다.

## 오늘의 정리

- 의미 중심 색상 토큰과 다크·라이트 모드 매핑을 정리했다.
- 글꼴, 8px 간격, 모서리·테두리·그림자 규칙을 만들었다.
- 공통 컴포넌트의 용도, 크기와 상태별 변형을 설계했다.
- 사용자 흐름, 복습 규칙과 서버·AI의 역할을 발표 자료로 완성했다.
- 데이터 관계, 권한, 기술 구성, MVP 순서와 위험 대응을 문서화했다.
- 오늘의 결과물은 기능 구현 완료가 아니라 이후 개발의 기준이 되는 디자인·기획 산출물이다.
